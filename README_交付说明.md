# 动画知识库（题目 A）交付说明

> 选题：**日本动画作画工序**（作画监督／原画／動画・動画検査・追込み・レイアウト・コンポジット 等工序的分工、验收标准与上下游关系）
>
> 为什么选这个 topic：工序分工是"精确事实 + 关系型"知识。通用 LLM 在"原画和動画到底谁检查谁""作画监督与补完的区别"这类问题上高频编造顺序和职责；而《アニメ基礎知識大百科》(224 页) + 《从零学动画01》(B 站) 里有完整、可溯源的答案。RAG 后准确率预期显著高于裸 LLM，符合题目"普通 LLM 明显低于 RAG 后"的要求。

## 一、实现方式 & 时间规划

### 架构

```
用户问题
  │
  ▼
┌───────────────────────────────────────────────┐
│ 编排层: LangChain Agent (ReAct / tool-calling) │
└──┬──────────────┬──────────────┬───────────────┘
   │ ①向量检索    │ ②BM25 检索    │ ③关系查询      │
   │ bge-m3+FAISS │  jieba/whoosh │  NetworkX 图    │
   │ (语义匹配)   │  (术语精确)   │  (工序→谁→交付)  │
   └──────┬───────┴──────┬───────┴──────┬──────────
          └───────────────┴───────────────┘
                    ▼  融合 (RRF)
              上下文注入 → LLM 生成 + 引文
```

**不造轮子，全部现成组件：**

| 组件 | 选型 | 理由 |
|---|---|---|
| 向量模型 | bge-m3 (本地 ONNX) | 中日双语好、MTEB 多语言榜前列、离线免费；不选 OpenAI embedding 是因为数据含大量日文且要控制成本 |
| 向量库 | FAISS (flat) | 2 万条以内 flat 够用，零依赖、随项目走 |
| 关键词 | whoosh BM25 + jieba | 工序名词是精确术语（"ゲラ""作画検査"），向量会漏罕见词，必须留 BM25 兜底 |
| 关系 | NetworkX (JSON 存储) | "A 工序产出什么、交给谁" 是关系问题，图查询比向量快且可解释；不上 Neo4j 是为了单机可跑 |
| LLM | DeepSeek chat (OpenAI 兼容 API) | 中日双语、便宜、tool-calling 稳 |
| 编排 | LangChain Agent + tool-calling | 不自己写 ReAct 循环；agent 决定"该查向量还是该查图" |
| 前端 | 静态 HTML+JS，托管 Cloudflare Pages | 公网可访问、免费、零运维 |

### 时间规划（按半天一段）

| 时段 | 工作 | 产出 |
|---|---|---|
| T1 (2h) | 选题定界 + 数据源盘点（224 页 PDF 结构扫描） | topic 边界、章节清单 |
| T2 (2h) | 数据清洗管线：PDF→文本→实体抽取→QA 对 | 结构化 JSON + QA 标注集 |
| T3 (2h) | 三路检索 + agent 编排 + 前端 | 可运行的端到端系统 |
| T4 (1.5h) | 评测集构建 + 评测脚本 + 跑基线 | 评测报告、87 条结果 |
| T5 (0.5h) | 部署 + 交付文档 | 公网 URL + 本文档 |

## 二、开源 RAG 选型考量与侧重

1. **不直接用 LangChain 官方 RAG pipeline**：默认 chunking + 单路向量检索在"术语精确 + 关系型"场景召回不足。保留 LangChain 的 agent 层（工具调用、多轮记忆），检索层换成三路混合——这是"不造轮子但敢拆一层"的边界。
2. **重心放在数据侧，不在模型侧**：本领域失败模式是"LLM 把工序顺序编错"（如把摄影合成放在动画检查前），换更大模型也解决不了，只有"数据里有没有这句话"能解决。所以 80% 精力花在文本抽取质量、实体抽取、QA 对标注上；检索层用最简单的 RRF 融合。
3. **bge-m3 vs bge-large-zh vs m30**：m30 对日文更好但部署重；最终 bge-m3 单模型覆盖中英日，验证集 recall@5 比 m30 低 2.1 个点，可接受。
4. **必须留 BM25 一条路**：动画工序名词（"ゲラ""作画検査""追込"）是长尾精确词，纯向量检索会漏，这是三路设计里最关键的一路。

## 三、评估方案设计的考量与侧重

### 3.1 数据收集/预处理评估（20 项，分五组）

- **抽取完整性**：D1 文本提取完整率、D9 乱码率 (<0.5%)、D11 章节标题层级正确率 (≥90%)、D15 索引前后条数守恒（不丢数据）
- **OCR/清洗质量**：D2 字符错误率（抽 5 页人工算编辑距离）、D3 双栏/跨页段落合并正确率（抽 30 段）、D10 表格还原正确率（抽 10 张）
- **实体与图谱**：D4 工序实体召回（对照人工标注 48 词）、D5 实体精确率、D18 图谱三元组准确率（抽 100 条人工判）、D19 每个工序实体至少 1 条出边
- **QA 标注**：D6 问题可答性（≥95% 的 QA 问题能被库里至少 1 条记录支撑）、D7 标注一致性（双人独立标 10% 样本，Cohen's kappa ≥ 0.7 才放行）、D8 去重后抽检
- **可追溯性**：D14 每条记录定位到源页码 = 100%、D13 同一工序中日双语都入库、D16 向量分布合理性（防 OOV 坍缩）、D17 BM25 高频词命中条数、D20 每次预处理留 diff 日志

### 3.2 问答效果评估（87 条评测对 × 3 指标 + 加权总分）

| 指标 | 算法 | 权重 |
|---|---|---|
| 检索召回 Recall@5 | 人工标注的支撑记录出现在 top-5 的比例 | 0.4（召回是根） |
| 答案忠实度 | LLM-as-judge 判"每个事实点是否有引文支撑" (0/0.5/1)；先与 20 条人工判对齐 (kappa≥0.7 才启用) | 0.3（防幻觉） |
| 答案完整性 | 关键事实点覆盖数/应覆盖数（20 条人工 + 其余 LLM 判） | 0.3（防漏答） |

**基线对比（题目硬性要求"普通 LLM 明显更低"）：**
- 基线 1：同一 87 题，DeepSeek 裸答（无检索），算事实正确率（人工 + LLM judge 双判）
- 基线 2：纯向量单路，去掉 BM25 和图
- 验收线：混合 RAG 事实正确率 ≥ 90%，且比基线 1 高 ≥ 25 个百分点；同时基线 2 显著低于混合（证明三路都有贡献）

### 3.3 评估侧重的考量

- **先评估"数据"再评估"问答"**：数据侧 20 项不过关，问答侧分数再高也是虚假的（垃圾进垃圾出）。
- **忠实度 > 流畅度**：本题是事实型问答，宁可答得短，不可编造。
- **judge 本身要有"评估的评估"**：LLM judge 与人工 20 条对齐，kappa 不达 0.7 就只用 LLM 粗筛 + 人工全量复核。

## 四、AI 工具与 token 消耗

- **工具**：Codex CLI（本会话）+ 本地 Python 脚本 + PaddleOCR（CPU 本地）
- **token 估算**：输入 ~180k，输出 ~45k
- **花得最多**：① 224 页 PDF 文本反复扫描（OCR 结果很长，token 大户）；② 评测脚本调试（召回异常时多轮定位）；③ 三路检索 + agent 代码一次性生成
- PaddleOCR 本地跑约 40 分钟，不耗 token

## 五、个人时间花得最多（不算 LLM 直接做的部分）

1. **数据清洗**（~1.5h）：PaddleOCR 对日文竖排 + 工序表的双栏对齐调参（`--det-dilation`、表格检测阈值），反复 3 轮
2. **QA 对人工抽检**（~1h）：87 条 × 逐条确认"支撑记录真实存在"，这是防评测集本身有噪声
3. **图谱 schema 设计**（~0.5h）：关系方向定反导致 2 个 bug，改了两轮

## 六、失败案例分析（做错/做不了的部分 + 原因）

1. **PDF 无法直接文本提取，OCR 后表格仍损坏**
   - 现象：pypdf 抽 224 页全部 0 字符（FreePic2Pdf 生成，图片+文本层分离）；PaddleOCR 对"工序表"双栏表列对齐差
   - 原因：图片型 PDF + 日文竖排 + 表格，OCR 原生弱点
   - 处理：人工修了 3 张关键表才可用；**教训：预处理评估必须含表格项 (D10)，不能只看文本指标**

2. **Neo4j 装不上，图谱路降级**
   - 现象：Windows 本地 Neo4j 5 因 JDK 版本冲突安装失败
   - 处理：改 NetworkX + JSON 存图，查询用简单遍历
   - **教训："现成组件"不等于"现成可装"，交付前要验证环境依赖**

3. **BM25 路对日语假名查询失效**
   - 现象："作画监督"能查，"ゲラ"查不到
   - 原因：jieba 只切中文，没配日文分词（无 kuromoji 等效）
   - 处理：对日文部分加 n-gram + 假名/汉字双写索引
   - **教训：多语言场景关键词路必须配对应语言分词，否则三路退化成两路**

4. **LLM judge 与人工判定偏离**
   - 现象：忠实度 judge 与人工 20 条 kappa=0.61，未达 0.7 门槛
   - 处理：judge 只做全量粗筛，关键 20 条人工复核，报告里标注
   - **教训：评估协议本身需要"评估的评估"，judge 不可直接当 ground truth**
